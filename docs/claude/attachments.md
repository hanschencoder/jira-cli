# 附件（改 `issue download` / `attachments` 前读）

## 必须落盘

Jira Server 的附件 `content` URL **要带认证头**才能取，裸链接给出去下不动。所以只能由工具带认证下载后落盘，输出**本地绝对路径**清单。

## 落点

默认 `<platformdirs.user_cache_dir>/attachments/<KEY>/`（Linux 下 `~/.cache/jira-cli/`），**不是当前工作目录**——否则在用户代码仓库里跑就把日志截图撒进去了。`download_dir` 配置项改根目录；`--dir` 单次平铺覆盖（不再套 `<KEY>/` 那层）。

## 缓存

下载前按「同路径 + 大小一致」判命中，命中则跳过并标 `cached: true`。判据够用的原因：**Jira 的附件不可变**——改内容只能删了重传，会得到新 id。文件被截断时大小对不上会自动重下。`--force` 忽略缓存。

## 文件名不可信

`filename` 由上传者控制，**不能直接拿来拼路径**。`Path(dir) / "../../x"` 会逃出落点，`Path(dir) / "/etc/cron.d/x"` 更是直接丢掉落点按绝对路径写——本工具是给 AI 自动调用的，一句 `issue download` 就落盘，等于把任意文件写入的能力交给了任何能往 issue 挂附件的人。

`_safe_name()` 只取基名（`PurePosixPath(...).name`，反斜杠先归一成 `/`，空名与 `.` / `..` 退化成 `attachment-<id>`），落盘前再校验 `dest.parent` 仍等于目标目录。

## 同名附件

**同一 issue 允许挂同名附件**（实测两个 `same-name.txt`，id 与大小均不同）。不做区分会互相覆盖：报告下载 N 个、磁盘上只有 1 个且大小对不上。

落盘名按**全部附件**判重后插 id 区分（`same-name.6056658.txt`）。必须基于全量而非本次筛选的子集，否则加不加 `--match` 得到的路径不一致、缓存命不中。

判重在**净化之后**做：`a/x.txt` 与 `b/x.txt` 取完基名都是 `x.txt`，不一起加 id 又会互相覆盖。

## 断点残留

先写 `<目标名>.part` 再 `replace()` 改名。中途断网或 Ctrl-C 时删掉 `.part`，落点不会留下一个大小不对的半截文件——那种文件看起来「下好了」，读的人拿到的却是截断内容。`download_attachment` 不经过 `request()`，所以要自己把 `RequestException` 包成 `ApiError`。

## 体积闸门

单次**实际要走网络**的字节数超过 `download_limit_mb`（默认 200）时拒绝执行，列出清单和缩小范围的办法，需 `-y` 放行。

闸门**只统计未命中缓存的部分**——否则重复跑同一个 issue 会莫名被拦，缓存等于白做。

实测该实例上单条 issue 附件合计 2.54 GB（5 个各 499 MB 的分卷），另一条挂 132 个附件。不设闸门会毫无预警地拖满带宽。
